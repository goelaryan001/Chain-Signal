Phase 0 · 6 Oct 2026

Environment: ClickHouse, Python, Spark

branch phase-0-environmentcommits e957eb4 → 3a5ec64 → 5c6239ctests 3 passing

Goal: have every tool the later phases need installed and proven working before writing any pipeline logic. If ClickHouse or Spark were broken we would find out now, not halfway through feature engineering.

  1. Checked the machine

    Found Docker 29.7 (installed but not running, so we launched Docker Desktop), Python 3.8 as the default, Python 3.11 and 3.12 available, and Java 21.

    Why it mattered: Spark runs on the Java Virtual Machine. Spark 3.5 only officially supports Java 8, 11 and 17. Spark 4.0 supports Java 17 and 21. Since this machine has Java 21, we chose PySpark 4.0 instead of installing a second Java. Python 3.8 is too old for current pandas and PySpark 4, so the project uses 3.11.

  2. Committed the design doc and made a working branch

    The design plan went in as its own commit (e957eb4) so the starting spec is preserved in history. All Phase 0 work happens on phase-0-environment, which keeps main clean until you merge.

  3. Ran ClickHouse in Docker

    docker-compose.yml defines one container from the official clickhouse/clickhouse-server:25.8 image.

    SettingWhat it does
    port 8123HTTP interface. Our Python client (clickhouse-connect) talks over this.
    port 9000Native TCP interface, for the clickhouse-client command line tool if you want to poke around.
    user / dbCreates user chainsignal and database chainsignal on first start, instead of using the default passwordless user.
    named volumeclickhouse-data keeps the data when the container stops or is recreated. docker compose down -v wipes it.
    ulimits nofileClickHouse opens many files at once (one per column per data part). The official image recommends raising the open-file limit.
    healthcheckPings /ping every 5 s so docker compose ps shows "healthy" only once it actually accepts queries.

    Why ClickHouse: it is a columnar database built for fast aggregations over large append-only data. Our access pattern is exactly that: load big batches of prices and transactions once, then run many "average / std / count over a window per coin" queries. Columnar storage reads only the columns a query touches and compresses repeated values well.

  5. Wrote the project skeleton and three small helpers

    src/chainsignal/
  config.py        reads settings from .env into one Settings object
  spark.py         get_spark(): local SparkSession, UTC time zone
  db/clickhouse.py get_client(): ClickHouse connection from settings
  ingest/  features/  models/  evaluation/   (empty, filled in later phases)
scripts/check_env.py
tests/test_environment.py

    Why helpers now: every later phase needs a database connection and a Spark session. Putting the connection details in one place means changing a host or password is a one-line edit in .env. Spark's time zone is pinned to UTC because crypto trades around the clock and both APIs return UTC timestamps; a local time zone would silently shift daily buckets.

    Secrets: .env holds real API keys and is git-ignored. .env.example is committed as the template. data/ is also ignored because raw pulls can be re-fetched.

  6. Verified everything actually works

    scripts/check_env.py runs a real query against ClickHouse, runs a real Spark job, and reports which API keys are set. Output:

    [ok] ClickHouse 25.8.33.6 reachable, database 'chainsignal' [ok] Spark 4.0.4 ran a local job (sum 0..999999 = 499999500000) [todo] COINGECKO_API_KEY not set yet (needed in Phase 1) [todo] ETHERSCAN_API_KEY not set yet (needed in Phase 1)

    The pytest suite has 3 tests: settings defaults match docker-compose.yml, a ClickHouse round trip (SELECT 1 + 1), and a Spark job. Tests that need running services are marked integration. All 3 pass.

Bugs and surprises

  • Docker Desktop was not running. We launched it and it was up within a few seconds. No code change.
  • Java 21 rules out Spark 3.5, so we chose PySpark 4.0. Recorded in the comment in requirements.txt.
  • No code bugs in this phase.

Explain it out loud

  • Why ClickHouse over DuckDB or TimescaleDB? A columnar server database built for fast aggregations over huge append-only data, used in production by crypto and fintech teams for this workload.
  • Why Docker? Anyone can reproduce the database with one command, at the same version.
  • Why a check script before any logic? It proves the foundation works, so later failures point at new code rather than setup.

API keys added and verified

Both keys are in .env (git-ignored, never committed). Being present in the file does not prove a key works, so we made one cheap live call to each API:

CoinGecko GET /api/v3/ping → 200 "(V3) To the Moon!" Etherscan GET /v2/api?module=proxy&action=eth_blockNumber → 200, latest block 26,134,800

The Etherscan call uses the V2 API (/v2/api with chainid=1 for Ethereum mainnet). V1 endpoints are deprecated, so all Phase 1 ingestion will use V2.

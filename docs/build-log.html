Environment: ClickHouse, Python, Spark

branch phase-0-environmentcommits e957eb4 → 3a5ec64 → 5c6239ctests 3 passing

Goal: have every tool the later phases need installed and proven working before writing any pipeline logic. If ClickHouse or Spark were broken we would find out now, not halfway through feature engineering.

  1. Checked the machine

    Found Docker 29.7 (installed but not running, so we launched Docker Desktop), Python 3.8 as the default, Python 3.11 and 3.12 available, and Java 21.

    Why it mattered: Spark runs on the Java Virtual Machine. Spark 3.5 only officially supports Java 8, 11 and 17. Spark 4.0 supports Java 17 and 21. Since this machine has Java 21, we chose PySpark 4.0 instead of installing a second Java. Python 3.8 is too old for current pandas and PySpark 4, so the project uses 3.11.

  2. Committed the design doc and made a working branch

    The design plan went in as its own commit (e957eb4) so the starting spec is preserved in history. All Phase 0 work happens on phase-0-environment, which keeps main clean until you merge.

  3. Ran ClickHouse in Docker

    docker-compose.yml defines one container from the official clickhouse/clickhouse-server:25.8 image.

Our access pattern is exactly that: load big batches of prices and transactions once, then run many "average / std / count over a window per coin" queries. Columnar storage reads only the columns a query touches and compresses repeated values well.

Explain it out loud

  • Why ClickHouse over DuckDB or TimescaleDB? A columnar server database built for fast aggregations over huge append-only data, used in production by crypto and fintech teams for this workload.

Phase 1 · 6 Oct 2026

Real data ingestion: CoinGecko + Etherscan

branch phase-1-ingestioncommits e7819d1 → 8197f9ctests 13 unit passingbugs fixed 4

Goal: pull real data from both sources, at the scale the design calls for, and look at it closely before building anything on top. Two very different shapes of data: breadth (1,000 coins, one row per coin per day) and depth (every single on-chain transfer of 3 tokens over 90 days).

  1. Confirmed the real API limits before writing code

    The design doc listed limits from memory. The ingestion design depends on them, so we checked both providers' current docs first.

    APILimitWhat it forced in the design
    CoinGecko Demo100 calls/minPace calls at ~92/min to leave headroom.
    CoinGecko Demo10,000 calls/monthThe real constraint: a 1,000-coin pull costs ~10% of the month. Every response is cached to disk and never fetched twice.
    CoinGecko Demo365 days of daily historyOur market window is exactly one year: 7 Oct 2025 to 6 Oct 2026.
    Etherscan free5 calls/sec, 100k/dayPace at 4/sec (later 1.6/sec per parallel process).
    Etherscan free1,000 records per request (since 1 Jul 2026)Pagination by block range, explained in step 4.

  2. Chose the three on-chain tokens

    TokenWhy it's in the set
    LINKSteady large-cap. The "normal behaviour" baseline.
    PEPEHigh-volume memecoin. Bursty, volatile activity.
    LOOKSLooksRare. Has a well-documented wash-trading history, which gives the anomaly hunt a named, real target.

    Contract addresses are looked up from CoinGecko's coin detail endpoint, not typed from memory, and saved in data/raw/etherscan/contracts.json. A wrong address would silently pull the wrong token's data.

  3. Wrote the CoinGecko client

    ingest/coingecko.py: 4 calls to /coins/markets fetch the top 1,000 coins by market cap (250 per page). Then one /coins/{id}/market_chart call per coin returns 365 days of price, market cap and volume. Each response is written to data/raw/coingecko/market_chart/<coin>.json, and coins already on disk are skipped. A crash halfway costs nothing.

    A subtle detail: CoinGecko's daily series has one point at 00:00 UTC per day, plus one extra point for "right now" in the middle of today. That last point is an incomplete day, so the parser keeps only exact-midnight points. Otherwise today would look like a day with strangely low volume.

    Correction found later (Phase 5, Bug 9): the midnight point stamped day D holds the close and 24-hour volume of day D−1, but this parser labelled it D. Every market date was one day late until Phase 5, when Celer's volume spike was compared with CoinRanking. Now fixed.

  4. Wrote the Etherscan client, with block-window pagination

    ingest/etherscan.py pulls ERC-20 Transfer events (tokentx) for each token. The hard part is getting every record exactly once when each request returns at most 1,000.

    Why not page 1, 2, 3...? Etherscan refuses requests where page × page size goes past 10,000 records. PEPE has 600k transfers in our window, so page numbers stop working almost immediately.

    Instead we walk forward by block number:

    ask:   transfers from block 1000 onward (max 1,000)
got:   1,000 records, blocks 1000 ... 1042
       block 1042 may be cut off part-way  →  drop it
write: everything in blocks 1000–1041 (complete blocks only)
next:  ask from block 1042 onward
...
got:   fewer than 1,000 records  →  reached the end, write all, done

    Because only complete blocks are ever written, there are no duplicates and no gaps, and the resume point is exact. After every batch a checkpoint (state.json) records the next block. A block holding more than 1,000 transfers of one token is paged on its own. The tests cover this case too.

  5. Tested the logic without the network

    The pagination function takes a "fetch" function as input. So the tests feed it a fake in-memory blockchain and check that every record comes back exactly once, that no block is split, that an oversized block is handled, and that resuming after a crash gives the same result as one clean run. Parsing tests cover decimals (LINK has 18: 1500000000000000000 raw = 1.5 LINK), lowercase addresses and UTC timestamps.

  6. Ran a small live trial before spending budget

    3 coins and 1 day of LOOKS, written to a scratch folder. CoinGecko looked right: Bitcoin returned exactly 365 rows. Etherscan crashed, which was the point of the trial. See Bug 2 below.

  7. Ran the full pulls, and sped them up

    CoinGecko ran at 42 coins/min, not the planned 92. Each request takes ~1.4 s on the server, and requests go one at a time. Etherscan ran at ~30 calls/min, about 2 s per call. Waiting on the server, not the rate limit, was the bottleneck. So the three tokens were split into three parallel processes at 1.6 calls/sec each (4.8/sec total, under the 5/sec limit).

    Two changes were needed first, because stopping and restarting a pull had to be safe:

    • range.json pins one block range (25,490,683 → 26,136,169, ~90 days) so all three tokens cover exactly the same window.
    • On resume, the data file is trimmed back to the checkpoint's row count. A kill landing between "write batch" and "save checkpoint" can no longer duplicate a batch.

    Midway, Etherscan slowed from ~2 s to ~9 s per call, and LINK and PEPE both crashed (Bug 3). After the fix, both resumed from their checkpoints with nothing lost. Then both reported "complete", yet their data stopped two days short of the end block (Bug 4). The inspection step caught it, and --recheck filled the gap: +19,023 LINK and +15,307 PEPE transfers.

  8. Inspected the real data

    scripts/inspect_raw.py loads everything and prints samples and sanity checks.

    DatasetRowsNotes
    CoinGecko319,1581,000 coins × up to 365 days, 0 failed fetches, ~1,010 of 10,000 monthly calls used. 291 coins listed within the year (shorter history). 0 null prices.
    LINK1,012,9361,025 API calls · 180,074 unique addresses · median 10,146 transfers/day
    PEPE622,132651 API calls · 168,172 unique addresses · median 5,536 transfers/day, peak 58,162 on 16 Jul
    LOOKS3,8564 API calls · 1,132 unique addresses · median 28 transfers/day, peak 388 on 7 Sep

    Duplicate check on (tx_hash, tx_seq): 0 duplicates for all three tokens. That's the pagination design proven on real data. Sanity check against reality on the latest day: BTC $85,771, ETH $2,710, USDT $1.00.

    Early on-chain observations to follow up in Phase 3:

    • LINK is busier on-chain than PEPE, even though PEPE is the "hype" token.
    • Many of PEPE's transfers come from handleOps (ERC-4337 smart-contract wallets) and from an oddly named unverified function, atInversebrah. Names like that are typical of MEV trading bots. That's automated activity, which matters when we ask what "normal" volume looks like.
    • LOOKS is nearly dormant: about 28 transfers a day, from just 1,132 addresses in 90 days. In such a thin market, a few wallets trading back and forth would stand out sharply.

Finding: feed glitches that look exactly like anomalies

Explain it out loud

  • How did you paginate around the 1,000-record cap? By block range, not page number. Drop the possibly cut-off last block of every full batch and restart from it, so only complete blocks are written. No duplicates, no gaps, exact resume.
  • How did you protect the 10k/month CoinGecko budget? Every response is cached to disk, and reruns skip what exists. A trial run went to a scratch folder first.
  • Why was it slow, and what did you do? Measured it first: waiting on the server, not the rate limit. So we parallelised across tokens while staying under the limit, after making restarts safe.
  • How do you know the data is complete? Two independent checks: zero duplicates on (tx_hash, tx_seq), and a coverage check that the last stored transfer reaches the end of the range. The second one caught a pull that had wrongly reported itself complete.
  • What surprised you in the data? The largest "anomalies" were feed glitches (bad prints, TAO/USD unit switches). That's why data cleaning comes before anomaly detection.
Phase 2 · 6 Oct 2026

ClickHouse schema, load and cleaning layer

branch phase-2-clickhousecommits b9ccbb7 → ab92530tests 22 passing (17 unit, 5 live-database)load verification 15/15

Goal: put the raw data into ClickHouse in tables designed for how we'll query them, prove that nothing was lost or changed in the move, and build a cleaning layer for the feed glitches found in Phase 1, without ever modifying the raw data.

  1. Designed the tables around how they'll be queried

    In ClickHouse, the ORDER BY of a MergeTree table is how rows are physically sorted on disk, and it doubles as the index. So the most important schema decision is: what will most queries filter on?

    TableSort keyWhy
    coinscoin_id1,000-row lookup table: id, symbol, name, rank.
    market_daily_raw(coin_id, date)Features are "one coin over time", so each coin's year sits contiguous on disk.
    token_transfers_raw(token, block_time, tx_hash, tx_seq)Queries are "one token over a time window", which become range reads.
    token_daily(token, day)Rollup per token per day, rebuilt after each load.

    Other choices:

    • Monthly partitions (about 13): reloading or deleting a month drops whole folders instead of rewriting rows.
    • LowCardinality on coin ids, token symbols and function names. These have few distinct values, so ClickHouse stores a small dictionary plus integer codes. Addresses (~350k distinct) stay plain strings, because dictionaries only pay off below ~10k distinct values.
    • value_raw as UInt256. The exact on-chain integer. The PEPE checksum is ~9.6 × 10³², which would overflow a 64-bit integer. amount (divided by 1018) is a float for analytics.

  2. Made loading idempotent

    Every load drops the tables, recreates them from schema.sql and inserts everything from the raw files, in batches of 100k rows. The raw files are the source of truth, so running the load twice gives the same result. It never double-counts, and schema changes always apply. A full load takes ~20 seconds.

    Why the daily rollup is not a materialized view: ClickHouse's materialized views are insert triggers. They're great for streaming, where data arrives once. In a batch pipeline that reloads, the trigger fires again on every reload and silently double-counts unless you also clear its output. An explicit rollup.sql step after loading is simpler and easy to verify.

  3. Verified the load independently

    scripts/load_clickhouse.py doesn't trust the loader's own counts. It re-reads the raw files separately and compares against ClickHouse:

    [ok] market rows: files=319,158 clickhouse=319,158 · (coin, date) keys unique [ok] LINK rows 1,012,936 · keys unique · sum(value_raw) exact to the last digit [ok] PEPE rows 622,132 · keys unique · sum(value_raw) = 962,016,337,991,980,648,104,278,860,771,052 [ok] LOOKS rows 3,856 · keys unique · sum exact [ok] token_daily totals add back up to the raw counts for every token LOAD VERIFIED (15/15)

    The exact 256-bit sum is the strongest check. If any single transfer were missing, duplicated or had its value altered, the sum would differ.

  4. Measured compression, then changed the schema

    The transfers table compressed only 2.1x. A per-column breakdown showed hashes and addresses were 68% of the bytes. They're random hex text, which compresses badly, and text doubles their size (2 characters per byte). We tested two alternatives on a copy of the table:

    LayoutOn diskTypical queryReadable
    Plain String, default LZ4173 MB~25 msyes
    Binary FixedString(32/20) + codecs89 MB~17 msno, needs hex() everywhere
    String + ZSTD, Delta on block/time ✔96 MB~27 msyes

    Decision: keep readable strings and switch codecs. ZSTD's entropy coding recovers most of the hex overhead, and Delta stores the steadily increasing block numbers and times as small differences. That's 90% of the saving at no readability cost. At billions of rows, the binary layout would be worth its awkwardness, and the trade-off is recorded in schema.sql.

  5. Built the cleaning layer from evidence

    Before setting any threshold, we queried the loaded data. There are 324 day-over-day moves of more than 10x, across 41 coins, and only 101 of them snap back the next day. The rest are regime switches: Bittensor subnet tokens sit at the wrong price for weeks, and they flip on the same dates (19 Jan, 10 Feb, 23 Apr, 31 May). That's one systematic feed problem, not many separate glitches.

    StatusRuleCoinsReasoning
    feed_glitch2+ moves >10x28Every multi-jump coin we inspected was a glitch, e.g. a tokenized treasury bill "falling 96%" then rebounding 24x.
    stale_feed>20% zero-volume days55A price is published but no one trades. 47 coins have zero volume on half their days.
    okeverything else917294,684 rows. The modelling input.

    Coins with exactly one extreme move are kept, with that row flagged (11 rows). Several look like real events, and those are exactly what the detector should find: power-protocol −90% on $48M volume, bulla-3 −94% on $34M (rug-pull shapes), a-meme-coin 726x on $276M (a launch pump). Phase 5 judges them.

    All of this is three SQL views (market_daily_flagged → coin_quality → market_daily_clean). The raw table is untouched, and every exclusion is visible and reversible in coin_quality.

  6. Tests

    Unit tests for the SQL splitter and the row builder (column order, exact UInt256 values). Five live-database tests check the loaded result itself: no excluded coin leaks into the clean view; no clean coin has repeated extreme moves; the first row of each coin is never flagged (it has no previous price); the rollup totals match the raw table; only the two edge days of the window are marked partial. 22 tests pass.

  7. A first look at back-and-forth trading, and a warning

    A quick query found address pairs sending the same token both ways, at least 5 times each direction. It scanned all 1.64M transfers in under half a second, and found 2,340 such pairs for LINK, 765 for PEPE and 20 for LOOKS.

    But the busiest pairs are not wash traders. One address appears in 5 of the top 8 pairs, across both LINK and PEPE. That's the shape of a DEX pool or router contract, which trades with everyone. Another starts with 0x00000000…, a vanity prefix common for MEV bots. So contracts must be separated from ordinary wallets before hunting wash trading, or the detector will "discover" Uniswap. This shapes the Phase 3 on-chain features.

Bugs and surprises

  • No code bugs this phase. The load passed verification on the first run.
  • Surprise 1: hashes and addresses were 68% of storage. That led to the codec change (173 → 96 MB).
  • Surprise 2: the >10x glitches come in synchronized waves across Bittensor tokens, so we exclude by coin, not by row.
  • Surprise 3: the most "suspicious-looking" back-and-forth pairs are infrastructure contracts.
  • Correction found later (Phase 4): the cleaning layer only checked prices. Volume has feed glitches too: Bitcoin shows $0.38B on 12 Mar 2026 between days of $35–46B. A volume_glitch flag (an isolated one-day collapse below 5% of both neighbours) now removes 921 such days across 179 coins from market_daily_clean.

Explain it out loud

  • Why ClickHouse? A columnar store that reads only the columns a query touches, with sort-key indexes and per-column codecs. Our workload is append-once, aggregate-many: exactly its design point. Scanning all 1.64M transfers to group address pairs took under 0.5 s on a laptop.
  • How did you choose the sort keys? From the queries: per coin over time, per token over a time window.
  • How do you know the load is right? An independent recount from the raw files, key uniqueness, and an exact 256-bit checksum of every value.
  • How did you clean the data without biasing it? Thresholds came from inspecting the data. Exclusions are by coin, visible in a view and reversible. Single extreme moves are kept, because they might be the real anomalies we're looking for.
  • Why not a materialized view? They're insert triggers, so batch reloads would double-count. An explicit rollup step is simpler to verify.
Phase 3 · 6 Oct 2026

Feature engineering with PySpark

branch phase-3-featurescommits 3af903a → 5b0fa42tests 33 passingpipeline checks 5/5bugs fixed 2

Goal: turn the cleaned data into features that describe "normal" for each coin and token, so that Phase 4's models can recognise departures from it. Carrying the warning from Phase 2: round-trip trading must be measured between ordinary wallets only, with pools, routers and bots separated out first.

Note added in Phase 5: market dates quoted in this entry are one day late (Bug 9, fixed in Phase 5). For example, Celer's volume spike was 3 June, not 4 June, and Bitcoin's volume glitch was 11 March, not 12 March. The statistics are unaffected.

  1. Labelled addresses as contract or wallet

    An address's appearance says nothing about what it is. The "ordinary sender" we printed as a sample in Phase 1 turned out to be the Wrapped LOOKS token contract. So we asked Etherscan instead: its getcontractcreation endpoint returns creation details for any contract among up to 5 addresses, and wallets simply don't appear in the answer.

    Only addresses taking part in a back-and-forth pair need a label: 13,204 of the 339,298. That's ~2,640 calls, run in 6 threads sharing one thread-safe rate limiter, cached and resumable. Result: 1,820 contracts (13.8%), 11,384 wallets.

    Known limitation: smart-contract wallets (Safe multisigs, ERC-4337 accounts) are contracts too, so they're grouped with pools and routers. Wash trading done through smart wallets would be missed.

  2. Moved data between ClickHouse and Spark via Parquet

    ClickHouse exports Parquet (93 MB in total), Spark reads it, computes the features and writes Parquet, and ClickHouse imports the result. That avoided a JDBC driver jar, both ends are columnar, and the files are checkpoints you can inspect. Dates cross the boundary as text and times as Unix seconds, because the two systems encode Parquet dates and timestamps differently, and silent conversion bugs there are common.

  3. Market features: 917 coins × 1 year

    The rule behind every feature: rolling statistics use only past days (rangeBetween(-30, -1) over calendar days). If today were in its own baseline, a spike would partly hide itself. That's lookahead leakage.

    FeatureMeaning
    return_z, volume_zHow unusual today's price move and volume are versus the coin's previous 30 days.
    turnover_zVolume ÷ market cap, standardized. Wash trading inflates turnover.
    market_corr, market_betaRolling relationship with the market (the median return of all clean coins, so BTC and stablecoins don't dominate).
    residual_zThe part of today's move the market doesn't explain, scaled by idiosyncratic volatility, σ·√(1−ρ²).
    volume_price_gapvolume_z − |return_z|: a lot of trading with no price reaction. The wash-trading signature.

    Two more rules: a return that spans a missing day is discarded, since a multi-day return isn't comparable to a 1-day one; and no feature is emitted until a coin has 20 days of history.

  4. On-chain features: 3 tokens × 88–89 full days

    FeatureMeaning
    rt_transfers, rt_shareRound-trip legs: a wallet-to-wallet transfer a→b where b→a happened in the previous 7 days. Both sides must be labelled wallets. Trailing only: a transfer isn't marked by a reply that comes later.
    new_addressesAddresses seen for the first time that day. Real growth brings new participants; recycling doesn't.
    top10_sender_shareShare of the day's volume sent by the 10 biggest senders.
    large_transfersTransfers above the token's own 99th percentile.
    hub_shareShare of transfers touching an address with 1,000+ distinct counterparties (pool, router or exchange-like).
    activity_vs_participantstransfers_z − addresses_z: activity growing faster than the set of people doing it.

    Trailing windows are 14 days (with at least 10 days of history), since the on-chain pull is 90 days long. The first and last day of the window are partial and are dropped.

    Design change: the plan had a "wallet-to-wallet share of all transfers" feature. That needs a label for every one of the 339k addresses, about 68,000 API calls, so it was replaced by hub_share, which comes straight from the data.

  5. Tested every feature on hand-built data

    The features are pure functions over DataFrames, so 10 Spark tests build tiny datasets where the answer is known. A +0.5 return after 25 calm days must score z > 10. No features before 20 days of history. A return after a gap is dropped. A volume spike with a flat price gives a high gap score. A reply within 7 days is a round-trip leg but one after 8 days isn't. A pair involving a contract or an unlabelled address never counts. Partial edge days are dropped.

  6. Ran the pipeline and verified it

    [ok] market rows preserved: clean=294,684 features=294,684 [ok] no infinite market z-scores [ok] 273,727 rows with return_z across 917 coins (the rest are warm-up days) [ok] on-chain days = rollup days minus the 2 partial edges (LINK 89, PEPE 89, LOOKS 88) [ok] Spark's daily transfer counts match ClickHouse's rollup on every day of every token

Phase 4 · 6 Oct 2026

Model comparison: z-score vs Isolation Forest vs LOF

branch phase-4-modelscommit e83e69ctests 43 passingbugs / corrections 4

Goal: run the three candidate detectors on the same features and compare them deliberately. Where do they agree, where do they disagree, and what kind of anomaly does each one catch? There are no labels, so the comparison has to be designed carefully, and the first runs turned out to be as much a test of the data and the methods as of the anomalies.

Note added in Phase 5: market dates quoted in this entry are one day late (Bug 9, fixed in Phase 5). For example, Celer's volume spike was 3 June, not 4 June, and Bitcoin's volume glitch was 11 March, not 12 March. The statistics are unaffected.

  1. Gave all three methods the same inputs

    For every coin-day: robust z-scores of return, volume, turnover and market-adjusted (residual) return. Robust means using the trailing 30-day median and MAD (median absolute deviation) instead of mean and standard deviation, still excluding the current day. That responds to Phase 3's volume z of 201: a median isn't dragged around by one extreme value. Same inputs for all three means any difference comes from the method.

    MethodScoreExpected strength
    Z-scorelargest |z| across the 4 featuressingle-feature extremes, fully interpretable
    Isolation Foresthow few random splits isolate the pointglobal outliers, unusual combinations
    LOFthe point's density vs its 20 nearest neighbours'local outliers, odd relative to similar days

  2. Designed a fair comparison without ground truth

    The three scores live on different scales, so comparing raw values or "default thresholds" means nothing. Instead each method gets the same alert budget: it flags its top 1% of coin-days (2,545). Then we measure overlap (Jaccard), consensus (how many methods agree), and the type of what each flags: price shock, volume-only, both, another feature, or multivariate-only (no single feature extreme, only the combination).

  3. Tested the design doc's central claim on synthetic data

    A cloud where x and y move together, plus one point at (2, −2): each feature only 2σ, but far off the line. Result: the z-score misses it; Isolation Forest and LOF both catch it. Other tests: LOF finds a point just outside a dense cluster, robust z ignores one past extreme, and the alert budget is exact even with ties.

  4. First run, and four corrections

    The first run's numbers looked plausible, but reading the actual flagged rows showed four problems. Each was measured, fixed and re-run (details in the table below):

    • Bitcoin and Ethereum appeared as "wash trading" with negative volume z: volume feed glitches the Phase 2 cleaning had missed.
    • Robust z still reached 74,309, on stablecoins.
    • The wash-trading list counted volume collapses as well as spikes.
    • LOF's "top anomalies" included perfectly ordinary days of a tokenized treasury bond.

Explain it out loud

  • How do you compare detectors without labels? At an equal alert budget. Then overlap, consensus, and a breakdown by anomaly type of what each one catches.
  • Which method won? None alone. The z-score and Isolation Forest mostly agree (0.73) on this fat-tailed data; LOF sees different, local, multivariate anomalies (24% of its flags). Agreement across methods is the strongest signal.
  • Why robust z-scores, and why the floor? Mean and std get dragged by single extremes (z = 201). Median and MAD don't, but they still blow up on near-constant series (z = 74,309), so the scale has a minimum.
  • What would you have shipped wrongly without checking? Bitcoin as a wash-trading suspect (a volume feed glitch), and LOF alerts on a treasury bond's ordinary days (the duplicate-point artifact).
Phase 5 · 6 Oct 2026

Evaluation: planted anomalies and real events

branch phase-5-evaluationcommits e59aa06 → cd4057btests 48 passingbugs / corrections 3

Goal: there's no ground truth for crypto anomalies, so we combine the two techniques from the design doc. Synthetic injection plants anomalies we created ourselves, so we know the answer exactly. Backtesting checks the methods against real, independently documented events. Then we report the failures as plainly as the successes.

  1. Made evaluation score data exactly like production

    The Phase 4 scoring steps moved into a shared models/pipeline.py, used by both the model run and the evaluation, so there's no second copy that could drift. The refactor was checked by re-running Phase 4: identical results (460 / 2,252 / 2,671).

  2. Synthetic injection design

    • Planted in the raw data (returns, volume, market cap), before the robust features are computed, so each anomaly goes through the real feature code.
    • One per coin (887 sites), at a random day with 40+ days of history, so no two injections share a trailing window.
    • Three types: a price spike; a volume spike with the price unchanged (the wash-trading shape); and a combo, a price move on falling volume at half strength each, so neither feature is extreme alone.
    • Strength in each coin's own units: 3, 6, 12 and 24 times its trailing robust σ, so "6σ" means the same for a stablecoin and a memecoin.
    • Metrics: recall at the 1% alert budget, and precision@k, which is a lower bound because real unlabelled anomalies in the data count as misses.

  5. Checked the top wash-trading candidate against an outside source

    Celer Network, 3 June 2026: CoinGecko says $1.49B of volume on a coin with an $18M market cap (82x its whole value in one day), with the price flat, then $487M, then back to ~$2M. CoinRanking independently shows the same: $1.5B, then $513M. So it isn't one aggregator's glitch; the volume really was reported by exchanges. $1.5B traded with no price impact can't be genuine trading in an $18M coin. It's consistent with wash trading or fake exchange-reported volume, which is the pattern this project set out to find. The other candidates (pyth-network, ordinals, hyperlane, just) were not checked externally; pyth-network's late-August spike also coincided with the market-wide rally.

What the evaluation says, plainly

  • Detection needs about 12σ at a 1% budget. Below 6σ, every method catches only a few percent of planted anomalies. Crypto's own fat-tailed anomalies fill the budget first. A lower alert budget won't fix that; a larger one costs more false alarms.
  • The design doc's claim about Isolation Forest holds where it matters: on combination anomalies (a move on falling volume), IF recalls 43% vs the z-score's 11% at 12σ, and 99% vs 54% at 24σ. Phase 4 saw IF mirror the z-score on real data. Both are true: IF's advantage is specific to anomalies spread across features.
  • LOF is weak at catching big spikes: only 17% recall even at 24σ. A spike lands in the sparse tail next to other real extremes, so it looks locally normal. LOF's value is the local, multivariate anomalies of Phase 4, not this kind of spike.
  • Consensus (2+ methods) is the safest single rule: 85% recall at 24σ overall, with the z-score's interpretability.
  • Some real events are invisible to market data: the Kelp hack moved rsETH no more than ETH. On-chain features (flows out of the protocol) would be needed.
  • Market-wide and coin-specific anomalies need different detectors. The market-return series caught the February crash and found the August rally on its own.

Explain it out loud

  • How do you evaluate an anomaly detector without labels? Plant anomalies you control and measure recall and precision, then backtest against independently documented events. Report both, including the misses.
  • Which method is best? Depends on the anomaly. Single-feature spikes: z-score (interpretable, ~equal to IF). Combinations: Isolation Forest (43% vs 11%). Local oddities: LOF. Consensus is the best default.

Goal: turn the work into something that holds up when someone else reads it. Every claim has to be reproducible, every bug has to be guarded against coming back, and the README has to explain the decisions, not just the steps.

  1. Insights as a script, not hand-typed numbers

  3. The final README

    Written for someone reading the repo for the first time, such as an interviewer.     Each phase was built on its own branch, each branched from the one before. All of them were fast-forwarded into main, so main's history keeps every commit, every bug fix and every correction in order.

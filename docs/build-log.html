Phase 0 · 6 Oct 2026

Environment: ClickHouse, Python, Spark

branch phase-0-environmentcommits e957eb4 → 3a5ec64 → 5c6239ctests 3 passing

Goal: have every tool the later phases need installed and proven working before writing any pipeline logic. If ClickHouse or Spark were broken we would find out now, not halfway through feature engineering.

  1. Checked the machine

    Found Docker 29.7 (installed but not running, so we launched Docker Desktop), Python 3.8 as the default, Python 3.11 and 3.12 available, and Java 21.

    Why it mattered: Spark runs on the Java Virtual Machine. Spark 3.5 only officially supports Java 8, 11 and 17. Spark 4.0 supports Java 17 and 21. Since this machine has Java 21, we chose PySpark 4.0 instead of installing a second Java. Python 3.8 is too old for current pandas and PySpark 4, so the project uses 3.11.

  2. Committed the design doc and made a working branch

    The design plan went in as its own commit (e957eb4) so the starting spec is preserved in history. All Phase 0 work happens on phase-0-environment, which keeps main clean until you merge.

  3. Ran ClickHouse in Docker

    docker-compose.yml defines one container from the official clickhouse/clickhouse-server:25.8 image.

    SettingWhat it does
    port 8123HTTP interface. Our Python client (clickhouse-connect) talks over this.
    port 9000Native TCP interface, for the clickhouse-client command line tool if you want to poke around.
    user / dbCreates user chainsignal and database chainsignal on first start, instead of using the default passwordless user.
    named volumeclickhouse-data keeps the data when the container stops or is recreated. docker compose down -v wipes it.
    ulimits nofileClickHouse opens many files at once (one per column per data part). The official image recommends raising the open-file limit.
    healthcheckPings /ping every 5 s so docker compose ps shows "healthy" only once it actually accepts queries.

    Why ClickHouse: it is a columnar database built for fast aggregations over large append-only data. Our access pattern is exactly that: load big batches of prices and transactions once, then run many "average / std / count over a window per coin" queries. Columnar storage reads only the columns a query touches and compresses repeated values well.

  5. Wrote the project skeleton and three small helpers

    src/chainsignal/

    Why helpers now: every later phase needs a database connection and a Spark session. Putting the connection details in one place means changing a host or password is a one-line edit in .env. Spark's time zone is pinned to UTC because crypto trades around the clock and both APIs return UTC timestamps; a local time zone would silently shift daily buckets.

    Secrets: .env holds real API keys and is git-ignored. .env.example is committed as the template. data/ is also ignored because raw pulls can be re-fetched.

  6. Verified everything actually works

    The pytest suite has 3 tests: settings defaults match docker-compose.yml, a ClickHouse round trip (SELECT 1 + 1), and a Spark job. Tests that need running services are marked integration. All 3 pass.

  • Why ClickHouse over DuckDB or TimescaleDB? A columnar server database built for fast aggregations over huge append-only data, used in production by crypto and fintech teams for this workload.

Phase 1 · 6 Oct 2026

Real data ingestion: CoinGecko + Etherscan

branch phase-1-ingestioncommits e7819d1 → 8197f9ctests 13 unit passingbugs fixed 4

Goal: pull real data from both sources, at the scale the design calls for, and look at it closely before building anything on top. Two very different shapes of data: breadth (1,000 coins, one row per coin per day) and depth (every single on-chain transfer of 3 tokens over 90 days).

  1. Confirmed the real API limits before writing code

    The design doc listed limits from memory. The ingestion design depends on them, so we checked both providers' current docs first.

    APILimitWhat it forced in the design
    CoinGecko Demo100 calls/minPace calls at ~92/min to leave headroom.
    CoinGecko Demo10,000 calls/monthThe real constraint: a 1,000-coin pull costs ~10% of the month. Every response is cached to disk and never fetched twice.
    CoinGecko Demo365 days of daily historyOur market window is exactly one year: 7 Oct 2025 to 6 Oct 2026.
    Etherscan free5 calls/sec, 100k/dayPace at 4/sec (later 1.6/sec per parallel process).
    Etherscan free1,000 records per request (since 1 Jul 2026)Pagination by block range, explained in step 4.

  2. Chose the three on-chain tokens

    TokenWhy it's in the set
    LINKSteady large-cap. The "normal behaviour" baseline.
    PEPEHigh-volume memecoin. Bursty, volatile activity.
    LOOKSLooksRare. Has a well-documented wash-trading history, which gives the anomaly hunt a named, real target.

    Contract addresses are looked up from CoinGecko's coin detail endpoint, not typed from memory, and saved in data/raw/etherscan/contracts.json. A wrong address would silently pull the wrong token's data.

  3. Wrote the CoinGecko client

    ingest/coingecko.py: 4 calls to /coins/markets fetch the top 1,000 coins by market cap (250 per page). Then one /coins/{id}/market_chart call per coin returns 365 days of price, market cap and volume. Each response is written to data/raw/coingecko/market_chart/<coin>.json, and coins already on disk are skipped. A crash halfway costs nothing.

    A subtle detail: CoinGecko's daily series has one point at 00:00 UTC per day, plus one extra point for "right now" in the middle of today. That last point is an incomplete day, so the parser keeps only exact-midnight points. Otherwise today would look like a day with strangely low volume.

  4. Wrote the Etherscan client, with block-window pagination

    ingest/etherscan.py pulls ERC-20 Transfer events (tokentx) for each token. The hard part is getting every record exactly once when each request returns at most 1,000.

    Why not page 1, 2, 3...? Etherscan refuses requests where page × page size goes past 10,000 records. PEPE has 600k transfers in our window, so page numbers stop working almost immediately.

    Instead we walk forward by block number:

    ask:   transfers from block 1000 onward (max 1,000)
got:   1,000 records, blocks 1000 ... 1042
       block 1042 may be cut off part-way  →  drop it
write: everything in blocks 1000–1041 (complete blocks only)
next:  ask from block 1042 onward
...
got:   fewer than 1,000 records  →  reached the end, write all, done

    Because only complete blocks are ever written, there are no duplicates and no gaps, and the resume point is exact. After every batch a checkpoint (state.json) records the next block. A block holding more than 1,000 transfers of one token is paged on its own. The tests cover this case too.

  5. Tested the logic without the network

    The pagination function takes a "fetch" function as input. So the tests feed it a fake in-memory blockchain and check that every record comes back exactly once, that no block is split, that an oversized block is handled, and that resuming after a crash gives the same result as one clean run. Parsing tests cover decimals (LINK has 18: 1500000000000000000 raw = 1.5 LINK), lowercase addresses and UTC timestamps.

  6. Ran a small live trial before spending budget

    3 coins and 1 day of LOOKS, written to a scratch folder. CoinGecko looked right: Bitcoin returned exactly 365 rows. Etherscan crashed, which was the point of the trial. See Bug 2 below.

  7. Ran the full pulls, and sped them up

    CoinGecko ran at 42 coins/min, not the planned 92. Each request takes ~1.4 s on the server, and requests go one at a time. Etherscan ran at ~30 calls/min, about 2 s per call. Waiting on the server, not the rate limit, was the bottleneck. So the three tokens were split into three parallel processes at 1.6 calls/sec each (4.8/sec total, under the 5/sec limit).

    Two changes were needed first, because stopping and restarting a pull had to be safe:

    • range.json pins one block range (25,490,683 → 26,136,169, ~90 days) so all three tokens cover exactly the same window.
    • On resume, the data file is trimmed back to the checkpoint's row count. A kill landing between "write batch" and "save checkpoint" can no longer duplicate a batch.

    Midway, Etherscan slowed from ~2 s to ~9 s per call, and LINK and PEPE both crashed (Bug 3). After the fix, both resumed from their checkpoints with nothing lost. Then both reported "complete", yet their data stopped two days short of the end block (Bug 4). The inspection step caught it, and --recheck filled the gap: +19,023 LINK and +15,307 PEPE transfers.

  8. Inspected the real data

    scripts/inspect_raw.py loads everything and prints samples and sanity checks.

    DatasetRowsNotes
    CoinGecko319,1581,000 coins × up to 365 days, 0 failed fetches, ~1,010 of 10,000 monthly calls used. 291 coins listed within the year (shorter history). 0 null prices.
    LINK1,012,9361,025 API calls · 180,074 unique addresses · median 10,146 transfers/day
    PEPE622,132651 API calls · 168,172 unique addresses · median 5,536 transfers/day, peak 58,162 on 16 Jul
    LOOKS3,8564 API calls · 1,132 unique addresses · median 28 transfers/day, peak 388 on 7 Sep

    Duplicate check on (tx_hash, tx_seq): 0 duplicates for all three tokens. That's the pagination design proven on real data. Sanity check against reality on the latest day: BTC $85,771, ETH $2,710, USDT $1.00.

    Early on-chain observations to follow up in Phase 3:

    • LINK is busier on-chain than PEPE, even though PEPE is the "hype" token.
    • Many of PEPE's transfers come from handleOps (ERC-4337 smart-contract wallets) and from an oddly named unverified function, atInversebrah. Names like that are typical of MEV trading bots. That's automated activity, which matters when we ask what "normal" volume looks like.
    • LOOKS is nearly dormant: about 28 transfers a day, from just 1,132 addresses in 90 days. In such a thin market, a few wallets trading back and forth would stand out sharply.

Finding: feed glitches that look exactly like anomalies

The biggest "price moves" in the dataset aren't market events. They're data errors:

PatternExampleCause
Bad printspinksale trades ~$200 but some days show $0.0032, then snaps back. That shows up as a +71,848x "return".A broken price feed on a thin market.
Unit switchingtargon, templar, bitmind, affine, openkaito and others jump by ~130x, again and again.Bittensor subnet tokens sometimes quoted in TAO instead of USD. 1 TAO ≈ $130.
Missing days92 coins have gaps inside their history.3,029 coin-days absent from the feed.

37 of 1,000 coins have at least one >10x single-day jump. A naive detector would rank these as the most anomalous points in crypto. Decision: raw data stays untouched (it's the record of what the API said), and a data-quality cleaning step runs before any modelling. This becomes part of the Phase 2/3 design.

Explain it out loud

  • How did you paginate around the 1,000-record cap? By block range, not page number. Drop the possibly cut-off last block of every full batch and restart from it, so only complete blocks are written. No duplicates, no gaps, exact resume.
  • How did you protect the 10k/month CoinGecko budget? Every response is cached to disk, and reruns skip what exists. A trial run went to a scratch folder first.
  • Why was it slow, and what did you do? Measured it first: waiting on the server, not the rate limit. So we parallelised across tokens while staying under the limit, after making restarts safe.
  • How do you know the data is complete? Two independent checks: zero duplicates on (tx_hash, tx_seq), and a coverage check that the last stored transfer reaches the end of the range. The second one caught a pull that had wrongly reported itself complete.
  • What surprised you in the data? The largest "anomalies" were feed glitches (bad prints, TAO/USD unit switches). That's why data cleaning comes before anomaly detection.
